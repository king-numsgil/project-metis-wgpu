# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Bun/TypeScript game-engine monorepo backed by a Rust native addon. The packages are:

- **`packages/metis-native`** — Rust napi-rs crate that exposes WebGPU (wgpu 30) and SDL3 to Bun/Node, plus the asset loaders that belong below the FFI boundary: images (PNG/JPEG/TGA/WebP/HDR and KTX2) and a full **glTF 2.0 importer** that returns ready-to-bind GPU buffers/textures. Close to the WebGPU spec, with a small, explicitly-typed set of native-only wgpu extensions (`GPUNativeFeatureName`). See its own [`CLAUDE.md`](packages/metis-native/CLAUDE.md) for detailed build rules, napi-rs constraints, SDL3 quirks, and GPU pitfalls.
- **`packages/metis-game`** — TypeScript game consuming `metis-native` *and* `metis-engine` via `workspace:*`. Currently a 100-animated-point-light demo plus a joystick/keyboard input smoketest. It bootstraps its own window/adapter/device/surface and drives the engine without `RenderContext` — the reference consumer of metis-engine's caller-owned-device path.
- **`packages/metis-engine`** — WebGPU clustered-forward PBR renderer (HDR + auto-exposure post-processing, directional shadow mapping, HUD text + debug graph/tree widgets via `metis-native`'s `VectorContext`, and an opt-in timestamp-query GPU profiler), built on `metis-native` plus `metis-data` (its only other dependency — GPU struct layouts *and* all the vector/matrix math; `wgpu-matrix` was migrated off and dropped); depends on neither `metis-game` nor `metis-tui` (`metis-game` consumes *it*). Its `src/` is split into two independent subtrees: **`renderer/`** (the whole renderer, imported via `metis-engine/renderer`) and **`ecs/`** (a young archetype ECS with Structure-of-Arrays storage, imported via `metis-engine/ecs`; no `metis-data` dependency). See its own [`CLAUDE.md`](packages/metis-engine/CLAUDE.md).
- **`packages/metis-tui`** — standalone OpenTUI (`@opentui/core`/`@opentui/react`) terminal-UI ship-systems sim; doesn't depend on the other packages. See its own [`CLAUDE.md`](packages/metis-tui/CLAUDE.md).

## API docs — read these before reading source

Each of the two library packages has a **`DOC.md`**: a task-oriented API
reference (what to call, with signatures, recipes, and the invariants that break
things silently).

| Package | Doc | Ground truth |
|---|---|---|
| `metis-native` | [`DOC.md`](packages/metis-native/DOC.md) | `index.d.ts` — auto-generated by `napi build`, authoritative, never drifts |
| `metis-engine` | [`DOC.md`](packages/metis-engine/DOC.md) | the source — hand-maintained doc |
| `metis-data` | [`DOC.md`](packages/metis-data/DOC.md) | the source — hand-maintained doc |

**When working in any of these packages, read its `DOC.md` first.** It exists so you
don't have to read a dozen source files to recall an API. Fall back to source
only when the doc doesn't cover what you need, or when the task hinges on an
exact signature (for `metis-native`, prefer `index.d.ts` over the doc).

### Keeping the docs current is not optional

**Every change updates the affected package's `DOC.md` and `CLAUDE.md` in the
same change. No exceptions, no "I'll do it after", no "it's a small change".**

This is a hard rule, and it is the one most likely to be quietly skipped, because
the code works either way and nothing fails when a doc rots. That is exactly why
it needs stating: a stale doc is worse than no doc, because it will be *trusted*
— by the next session, by a subagent that reads it instead of the source, and by
the human who wrote neither. Real damage already caused by exactly this:
`metis-data`'s `CLAUDE.md` went on describing the ECS as its main consumer for
long after the ECS had dropped it, and would have justified optimizing that
package for a workload it no longer has.

Concretely, when a change touches any of these, the docs move with it:

- an exported symbol appearing, disappearing, or changing signature;
- a config constant's value or meaning;
- a required call order, ownership rule, or teardown order;
- a documented invariant, or a *reason* one exists;
- a dependency added or dropped;
- an architectural decision, including ones deliberately **declined** — record
  the "we measured this and rejected it" so it isn't re-litigated.

Which file gets the edit: `CLAUDE.md` explains *why* (architecture, rationale,
debugging history, roads not taken); `DOC.md` explains *what to call*
(signatures, recipes, invariants). Keep that split — don't duplicate war stories
into `DOC.md`, don't grow an API listing in `CLAUDE.md`.

If a change makes a doc statement false and you are not fixing it in that change,
you are not done with that change.

## Commands

All commands are run from the repo root unless noted.

```powershell
# Install all dependencies
bun install

# Build the Rust native addon (debug, from packages/metis-native)
cd packages/metis-native && bun run build:debug

# Optimized build for iterating on performance (default `build`, `fastdev`
# profile: opt-level 3, no LTO). ~19 s to rebuild after a one-line change,
# vs ~103 s for `build:release` — use this when profiling.
cd packages/metis-native && bun run build

# Real release build (fat LTO). Slow; for shipping, not for iterating.
cd packages/metis-native && bun run build:release

# Run all tests (from metis-native)
cd packages/metis-native && bun test

# Run a single test file
cd packages/metis-native && bun test test/render-window.test.ts --timeout 15000

# Type-check (root, covers metis-game via paths alias)
bunx tsc --noEmit

# Type-check metis-native binding types only
cd packages/metis-native && bunx tsc --noEmit

# Run metis-game
bun run packages/metis-game/src/index.ts
```

## Architecture

```
metis-wgpu/
  packages/
    metis-native/       Rust cdylib → .node file loaded by index.js
      src/
        lib.rs           Re-exports all public symbols; edit when adding new ones
        gpu/             WebGPU types: instance, adapter, device, surface, encoder, pipeline, …
        sdl/             SDL3 bindings: init, window, events, keyboard, mouse, joystick, gamepad
        image/           Image load/save (PNG/JPEG/TGA/WebP/HDR + KTX2) straight into wgpu textures
        gltf/            glTF 2.0 importer: inspectGltf (container only) + loadGltf (GPU + scene graph)
      index.js           Auto-generated by napi-rs; do not edit
      test/              Bun test files (.test.ts)
    metis-game/
      src/index.ts        Game entry point; a 100-point-light demo + joystick smoketest.
                          Owns its own window/adapter/device/surface and drives
                          metis-engine directly (metis-engine/DOC.md §1.3) — the
                          reference consumer of the caller-owned-device path.
```

### Data flow

1. Rust compiles to `metis-native.win32-x64-msvc.node` (or platform equivalent).
2. `index.js` (auto-generated by napi-rs) loads the `.node` file and re-exports all napi symbols.
3. `metis-game` imports from `metis-native` which resolves to `index.js`.

### Key conventions

- The root `tsconfig.json` maps `"metis-native"` to `./packages/metis-native` so the type-checker sees the `.d.ts` files without building.
- `napi-rs` is the only FFI layer — no raw N-API calls in JS.
- After any change to Rust source, rebuild with `bun run build:debug` before running tests or the game.
